01

왜 하네스를 이해해야 하나?Why Should You Understand the Harness?

AI 코딩은 "코드를 직접 고치는 단계"에서 "가이드를 설계하는 단계"로 진화하고 있습니다. AI coding is evolving from "manually fixing code" to "designing guides."

In the Loop vs On the LoopIn the Loop vs On the Loop

AI 코딩에는 두 가지 방식이 있습니다:

  🛠 Human In the Loop (2단계) → AI가 만든 코드를 한 줄씩 확인하고 직접 수정. Copilot, Cursor의 방식.
  🎯 Human On the Loop (3단계) → 가이드(하네스)를 설계해서 AI에게 자율 작업을 위임. 결과가 맞지 않으면 코드가 아니라 하네스를 개선.

Claude Code는 3단계 도구입니다. CLAUDE.md로 프로젝트 규칙을 정의하고, Skills로 워크플로우를 자동화하고, Hooks로 안전장치를 설정하는 것 — 이 모든 것이 "하네스 엔지니어링"입니다.

하네스의 구조를 이해하면 무엇을 설계해야 하는지가 명확해집니다.

There are two approaches to AI coding:

  🛠 Human In the Loop (Stage 2) → Review AI-generated code line by line and fix it directly. The Copilot/Cursor approach.
  🎯 Human On the Loop (Stage 3) → Design guides (harness) and delegate autonomous work to AI. When results are wrong, improve the harness, not the code.

Claude Code is a Stage 3 tool. Defining project rules with CLAUDE.md, automating workflows with Skills, setting up safety nets with Hooks — all of this is "harness engineering."

Understanding the harness structure makes it clear what you need to design.

하네스 없는 AI의 위험 — Amazon 사례AI Without a Harness — The Amazon Case

제대로 된 하네스(가이드, 권한, 검증) 없이 AI에게 자율권을 주면 어떻게 될까요?

2025.12 — Amazon의 AI 에이전트 'Kiro'가 무단으로 운영 서버를 삭제/재생성. 비용 계산기 시스템 13시간 다운.
2026.03.02 — AI가 생성한 코드가 장바구니 오류 유발. 12만 건 주문 손실.
2026.03.05 — 안전장치 없이 AI 코드가 배포되어 북미 주문의 99%가 증발. 하루 630만 건 주문 손실.

Amazon은 이후 모든 코드에 인간 교차 검증을 의무화했습니다. 이것이 하네스의 권한 관리와 Hooks가 존재하는 이유입니다. What happens when you give AI autonomy without a proper harness (guides, permissions, verification)?

2025.12 — Amazon's AI agent 'Kiro' unauthorized deletion/recreation of production servers. Cost calculator system down for 13 hours.
2026.03.02 — AI-generated code caused shopping cart errors. 120,000 orders lost.
2026.03.05 — AI code deployed without safety nets wiped out 99% of North American orders. 6.3 million orders lost in one day.

Amazon subsequently mandated human cross-verification for all code. This is exactly why the harness's permission management and Hooks exist.

참고: Terry Cho — AI 코딩의 발전단계 · Martin Fowler — Humans and Agents Reference: Terry Cho — AI Coding Stages · Martin Fowler — Humans and Agents

02

하네스가 대체 뭐야?What Exactly Is the Harness?

한 줄 요약: Claude 모델을 감싸서 실제로 동작하게 만드는 런타임 시스템이다. One-line summary: The runtime system that wraps the Claude model and makes it actually work.

오케스트라 지휘자 비유로 이해하기The Orchestra Conductor Analogy

Claude 모델은 아주 뛰어난 연주자입니다. 하지만 연주자 혼자서는 콘서트를 열 수 없습니다.

  🎹 연주자(Claude 모델) → 질문에 답하고, 코드를 생성하는 AI 두뇌
  🎴 지휘자(하네스) → 악보를 나눠주고, 순서를 정하고, 악기를 준비해주는 시스템

하네스 = 지휘자입니다.
"어떤 도구를 쓸지 결정하고, 권한을 확인하고, 파일을 읽어서 모델에게 전달하고, 결과를 받아서 실행하는" — 이 모든 과정을 관리합니다.

The Claude model is an incredibly talented musician. But a musician alone can't run a concert.

  🎹 Musician (Claude Model) → The AI brain that answers questions and generates code
  🎴 Conductor (Harness) → The system that distributes sheet music, sets the order, and prepares instruments

Harness = the Conductor.
It manages everything: "deciding which tools to use, checking permissions, reading files to pass to the model, and executing results."

⚙

모델이 아니다It's Not the Model

하네스는 AI 모델 자체가 아닙니다. 모델은 "생각하는 두뇌"이고, 하네스는 그 두뇌가 실제 세계와 상호작용할 수 있게 해주는 시스템입니다.

The harness isn't the AI model itself. The model is the "thinking brain" and the harness is the system that lets that brain interact with the real world.

🔄

루프를 돌린다Runs the Loop

하네스의 핵심은 에이전트 루프입니다. 모델에게 물어보고 → 도구를 실행하고 → 결과를 다시 모델에게 전달하는 과정을 반복합니다.

The core of the harness is the agent loop. It asks the model → executes tools → feeds results back to the model, repeating this cycle.

🛡

안전을 지킨다Keeps You Safe

권한 확인, 도구 승인, 위험한 명령 차단 등 안전 장치를 관리합니다. "이 파일을 수정해도 될까요?" 같은 질문이 하네스에서 나옵니다.

It manages safety mechanisms: permission checks, tool approvals, blocking dangerous commands. "Can I modify this file?" prompts come from the harness.

04

에이전트 루프 — 핵심 중의 핵심The Agent Loop — The Heart of Everything

하네스의 가장 중요한 역할은 이 루프를 반복하는 것입니다 The harness's most critical role is running this loop

요리사 비유로 이해하기The Chef Analogy

여러분이 "파스타 만들어줘"라고 말하면, 요리사(Claude)는 한 번에 완성하지 않습니다.

📝 레시피 확인(계획) → 🔪 재료 손질(도구 사용) → 👁 맛 확인(결과 검증) → 🧂 간 조절(수정) → ... → ✅ 완성!

이 "확인 → 실행 → 검증 → 반복" 과정이 바로 에이전트 루프이고, 하네스가 이 과정을 관리합니다.

When you say "make pasta," the chef (Claude) doesn't finish it all at once.

📝 Check recipe (plan) → 🔪 Prep ingredients (use tools) → 👁 Taste test (verify result) → 🧂 Adjust seasoning (modify) → ... → ✅ Done!

This "check → execute → verify → repeat" process is the agent loop, and the harness manages it all.

루프의 5단계The 5 Steps of the Loop

1

컨텍스트 조립Context Assembly

사용자 메시지 + CLAUDE.md + 시스템 프롬프트 + 이전 대화 + 도구 정의를 하나의 요청으로 묶어서 모델에게 전송합니다.Bundles user message + CLAUDE.md + system prompt + conversation history + tool definitions into a single request to the model.

2

모델 응답Model Response

Claude 모델이 텍스트 응답 또는 도구 호출 요청을 반환합니다. 예: "Read 도구로 src/app.ts를 읽겠습니다."The Claude model returns a text response or a tool call request. Example: "I'll use the Read tool to read src/app.ts."

3

권한 확인Permission Check

하네스가 권한 모드를 확인합니다. Normal Mode면 사용자에게 승인을 요청하고, Auto-Accept면 자동 실행합니다. Plan Mode면 도구 실행을 차단합니다.The harness checks the permission mode. In Normal Mode, it asks the user for approval. In Auto-Accept, it runs automatically. In Plan Mode, tool execution is blocked.

4

도구 실행 + HooksTool Execution + Hooks

승인되면 하네스가 도구를 실행합니다. 이때 설정된 Hooks가 있으면 도구 실행 전(PreToolUse)과 후(PostToolUse)에 사용자 스크립트를 실행합니다.Once approved, the harness executes the tool. If hooks are configured, it runs user scripts before (PreToolUse) and after (PostToolUse) tool execution.

5

결과 피드백 → 반복 또는 종료Result Feedback → Repeat or End

도구 실행 결과를 모델에게 다시 전달합니다. 모델이 "작업 완료"라고 판단하면 루프 종료. 추가 작업이 필요하면 2단계로 돌아갑니다.Feeds tool execution results back to the model. If the model decides "task complete," the loop ends. If more work is needed, it returns to step 2.

핵심 포인트Key Point

하나의 프롬프트에 대해 이 루프가 수십 번 반복될 수 있습니다. "이 프로젝트에 테스트를 추가해줘"라고 하면 Claude는 파일 읽기 → 분석 → 테스트 작성 → 실행 → 오류 수정 → 재실행을 반복합니다. 이 전체를 하네스가 관리합니다.This loop can repeat dozens of times for a single prompt. When you say "add tests to this project," Claude reads files → analyzes → writes tests → runs them → fixes errors → re-runs. The harness manages this entire process.

05

도구 디스패치 — 실제로 일하는 손Tool Dispatch — The Working Hands

모델이 "이 도구를 쓰겠다"고 말하면, 하네스가 실제 실행을 담당합니다 When the model says "I'll use this tool," the harness handles the actual execution

MCP 도구 (외부 확장)MCP Tools (External Extensions)

MCP 서버를 통해 추가된 외부 도구들입니다. 하네스는 이 도구들도 내장 도구와 동일하게 취급합니다.External tools added through MCP servers. The harness treats these the same as built-in tools.

bash
# MCP 도구도 하네스가 관리
# 1. 하네스가 MCP 서버에서 도구 정의를 가져옴
# 2. 모델에게 "이런 도구들이 있다"고 알려줌
# 3. 모델이 호출하면 하네스가 MCP 서버로 중계

claude mcp add --transport stdio github -- \
  npx -y @anthropic-ai/mcp-server-github

# 하네스가 github MCP의 도구들을 모델에게 등록
# → 모델: "search_repositories 도구로 검색하겠습니다"
# → 하네스: MCP 서버에 요청 전달 → 결과 반환
도구가 많을수록 컨텍스트가 줄어든다More Tools = Less Context

하네스는 모든 도구의 정의(설명, 파라미터)를 모델에게 전달해야 합니다. MCP 서버를 많이 연결하면 도구 정의만으로 컨텍스트 윈도우의 상당 부분을 차지합니다. 이것이 "MCP 10개 이상이면 컨텍스트가 급감한다"는 이유입니다.The harness must pass all tool definitions (descriptions, parameters) to the model. Connecting many MCP servers means tool definitions alone consume a significant portion of the context window. This is why "more than 10 MCPs causes context to plummet."

06

컨텍스트 조립 — 모델이 보는 세상Context Assembly — What the Model Sees

매 요청마다 하네스가 이 모든 것을 하나로 합쳐서 모델에게 보냅니다 For every request, the harness merges all of this and sends it to the model

컨텍스트에 포함되는 것들 (순서대로)What Goes Into Context (in order)

1

시스템 프롬프트System Prompt

Claude Code의 기본 행동 규칙. "파일을 읽을 때는 Read 도구를 사용하라", "보안 취약점을 만들지 마라" 등의 지침이 포함됩니다. 사용자가 수정할 수 없습니다.Claude Code's base behavior rules. Instructions like "use the Read tool to read files" and "don't create security vulnerabilities." Users can't modify this.

2

CLAUDE.md

전역(~/) → 프로젝트 루트 → 하위 디렉토리 순서로 병합됩니다. 사용자의 프로젝트별 지침이 여기에 해당합니다.Merged in order: global (~/) → project root → subdirectory. Your project-specific instructions go here.

3

도구 정의Tool Definitions

내장 도구 + MCP 도구 + Skills 설명. 모델이 어떤 도구를 사용할 수 있는지 알려줍니다.Built-in tools + MCP tools + Skills descriptions. Tells the model what tools are available.

4

대화 히스토리Conversation History

이전 메시지 + 도구 호출 결과. 대화가 길어지면 하네스가 자동으로 오래된 메시지를 압축합니다.Previous messages + tool call results. As conversation grows, the harness auto-compresses older messages.

5

현재 사용자 메시지Current User Message

방금 여러분이 입력한 프롬프트입니다.The prompt you just typed.

📦

자동 압축Auto Compression

대화가 컨텍스트 한계에 가까워지면 하네스가 자동으로 오래된 메시지를 요약합니다. /compact로 수동으로도 할 수 있고, 키워드를 지정해서 특정 내용만 남길 수도 있습니다.

When conversation approaches context limits, the harness automatically summarizes older messages. You can do this manually with /compact, or specify keywords to keep specific content.

📊

토큰 추적Token Tracking

The harness tracks tokens used per request. Use /cost to check current session token usage. Essential for API users to monitor costs.

왜 이걸 알아야 하나?Why Should You Know This?

컨텍스트 조립 과정을 이해하면 왜 CLAUDE.md를 짧게 써야 하는지, 왜 MCP를 너무 많이 달면 안 되는지, 왜 대화가 길어지면 성능이 떨어지는지를 정확히 알 수 있습니다. 모두 같은 컨텍스트 윈도우 안에서 경쟁하기 때문입니다.Understanding context assembly explains why CLAUDE.md should be concise, why too many MCPs hurt performance, and why long conversations degrade quality. Everything competes for the same context window.

권한 관리 — 안전 장치Permission Management — Safety Net

하네스는 모델이 위험한 행동을 하지 못하도록 보호합니다 The harness protects against the model performing dangerous actions

3가지 권한 모드3 Permission Modes

하네스가 도구 실행 요청을 받았을 때의 동작 방식입니다.How the harness behaves when it receives a tool execution request.

모드Mode하네스 동작Harness Behavior적합한 상황Best For
Normal파일 수정, 셸 실행 시 사용자에게 매번 승인 요청Asks for user approval on file changes and shell execution일반적인 작업 (기본값)Normal work (default)
Auto-Accept모든 도구를 자동 승인하여 실행Auto-approves all tools숙련자, 신뢰할 수 있는 작업Experienced users, trusted tasks

세밀한 권한 규칙Fine-grained Permission Rules

settings.json이나 /permissions에서 도구별, 경로별로 세밀하게 제어할 수 있습니다.You can set granular controls per tool and per path in settings.json or /permissions.

settings.json
// 예: 특정 도구 자동 허용/거부
{
  "permissions": {
    "allow": [
      "Read",
      "Grep",
      "Glob",
      "Bash(git status)",
      "Bash(npm test)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force)"
    ]
  }
}
이것이 하네스의 역할This Is the Harness's Role

모델은 "rm -rf 실행하겠습니다"라고 할 수 있지만, 하네스가 실제 실행을 차단합니다. 모델과 실제 실행 사이의 게이트키퍼가 바로 하네스입니다.The model might say "I'll run rm -rf" but the harness blocks the actual execution. The gatekeeper between the model and real execution is the harness.

Hooks — 하네스의 확장 포인트Hooks — The Harness Extension Point

Hooks는 하네스의 특정 시점에 사용자가 셸 스크립트를 끼워넣는 기능입니다.Hooks let users inject shell scripts at specific points in the harness lifecycle.

Hook시점When사용 예Use Case
PreToolUse도구 실행 전Before tool execution특정 파일 수정 차단, 자동 승인Block certain file edits, auto-approve
PostToolUse도구 실행 후After tool execution린터 실행, 알림 전송Run linter, send notifications
NotificationClaude가 입력 대기 시When Claude awaits input작업 완료 알림Task completion alert
Stop에이전트 루프 종료 시When agent loop ends자동 커밋, 로그 기록Auto-commit, logging
settings.json
// Hook 설정 예시: 파일 수정 후 자동으로 린터 실행
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          {
            "type": "command",
            "command": "npx eslint --fix $CLAUDE_FILE_PATH"
          }
        ]
      }
    ]
  }
}

자주 묻는 질문Frequently Asked Questions

하네스에 대해 처음 접하는 분들이 가장 많이 궁금해하는 것들 The most common questions from those new to the harness concept

모델은 텍스트를 입력받아 텍스트를 출력하는 AI입니다. "이 코드를 수정해야 합니다"라고 판단하는 것이 모델의 역할입니다.

하네스는 모델의 판단을 실행하는 시스템입니다. 실제로 파일을 읽고, 쓰고, 명령을 실행하는 것은 하네스입니다. 모델은 "무엇을 해야 하는지" 결정하고, 하네스는 "어떻게 실행할지"를 담당합니다.
The model is AI that takes text input and produces text output. Its role is to decide "this code needs to be modified."

The harness is the system that executes the model's decisions. It actually reads files, writes code, and runs commands. The model decides "what to do," the harness handles "how to do it."
하네스의 핵심 로직을 직접 수정하는 것은 불가능합니다. 하지만 하네스의 동작을 제어하는 많은 방법이 있습니다:

1. CLAUDE.md — 모델에게 주는 지침 커스터마이징
2. settings.json — 권한 규칙, 허용/거부 도구 설정
3. Hooks — 도구 실행 전후에 사용자 스크립트 실행
4. 권한 모드 — Normal/Auto-Accept/Plan 전환
5. MCP 서버 — 새로운 도구 추가

즉, 하네스 자체를 바꾸는 게 아니라, 하네스에게 "이렇게 동작해라"라고 설정하는 것입니다.
You can't directly modify the harness's core logic. But there are many ways to control its behavior:

1. CLAUDE.md — Customize instructions given to the model
2. settings.json — Set permission rules, allow/deny tools
3. Hooks — Run user scripts before/after tool execution
4. Permission modes — Switch between Normal/Auto-Accept/Plan
5. MCP servers — Add new tools

In other words, you don't change the harness itself — you configure how it behaves.
밀접하지만 다른 개념입니다.

"에이전트"는 모델 + 하네스가 합쳐진 전체 시스템을 의미합니다. "Claude Code 에이전트"라고 하면, AI 두뇌(모델)와 실행 시스템(하네스)을 모두 포함하는 개념입니다.

"하네스"는 그 에이전트 시스템에서 모델을 제외한 나머지 부분 — 즉 루프 관리, 도구 실행, 권한 제어 등의 인프라입니다.

비유하면: 에이전트 = 자동차 전체, 하네스 = 엔진을 제외한 차체·변속기·브레이크 시스템.
Related but different concepts.

"Agent" means the entire system of model + harness combined. When we say "Claude Code agent," it includes both the AI brain (model) and execution system (harness).

"Harness" is everything except the model in that agent system — the infrastructure for loop management, tool execution, permission control, etc.

Analogy: Agent = the whole car, Harness = the chassis, transmission, and brake system (everything except the engine).
1. 성능 최적화 — 컨텍스트 윈도우에서 무엇이 공간을 차지하는지 알면, CLAUDE.md를 간결하게 쓰고 MCP를 적절히 관리하는 이유를 이해합니다.

2. 문제 진단 — "Claude가 왜 이 파일을 못 찾지?"라는 질문에 "컨텍스트에 해당 정보가 없기 때문"이라는 정확한 원인을 파악할 수 있습니다.

3. 안전한 사용 — 권한 시스템이 어떻게 작동하는지 알면, 언제 Auto-Accept를 써도 되는지, 어떤 Hook을 설정해야 하는지 판단할 수 있습니다.

4. 효과적인 프롬프팅 — 모델이 받는 컨텍스트의 구조를 알면, 어떤 정보를 프롬프트에 포함해야 효과적인지 이해합니다.
1. Performance optimization — Knowing what occupies context window space helps you understand why to keep CLAUDE.md concise and manage MCPs carefully.

2. Problem diagnosis — When "Claude can't find this file," you can identify the exact cause: "that information isn't in the context."

3. Safe usage — Understanding how the permission system works helps you judge when Auto-Accept is safe and which Hooks to configure.

4. Effective prompting — Knowing the structure of context the model receives helps you understand what information to include in prompts.
네! 서브에이전트(Agent 도구로 생성)는 독립된 하네스 인스턴스에서 실행됩니다. 각각 자체 컨텍스트 윈도우, 자체 에이전트 루프를 가집니다. 메인 에이전트와 컨텍스트를 공유하지 않기 때문에, 서브에이전트에게 대량의 파일을 탐색시켜도 메인 에이전트의 컨텍스트가 오염되지 않습니다. 이것이 서브에이전트의 핵심 장점입니다.
Yes! Sub-agents (created via the Agent tool) run in independent harness instances. Each has its own context window and its own agent loop. Since they don't share context with the main agent, having a sub-agent search through many files won't pollute the main agent's context. This is the key advantage of sub-agents.
